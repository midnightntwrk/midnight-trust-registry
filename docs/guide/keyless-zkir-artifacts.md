# Keyless ZKIR Artifacts (local prototype)

Status: **not a release bundle or standalone installation path**. This guide
describes the local regeneration experiment tracked by [#281](https://github.com/midnightntwrk/midnight-trust-registry/issues/281).
The verified `0.1.0-rc1` bundle remains unchanged and still requires its packed
prover and verifier keys. Do not replace or relabel its manifest.

The pinned Compact 0.31.1 toolchain includes `zkir compile <IR_FILE>
<PROVER_KEY> <VERIFIER_KEY>`. A keyless managed-contract directory carries the
generated JavaScript, compiler metadata, both `.zkir` and `.bzkir` representations
of every proof circuit, and `keyless-manifest.json`. It does **not** carry
`.prover` or `.verifier` files. The manifest records the exact source revision,
compiler version, platform, key-generator binary digest, asset hashes, and
expected hashes for both keys of every proof circuit.

Run the following against full, retained outputs in a dedicated artifact-bearing
checkout. Do not run a light build there; it removes generated keys.

```sh
node scripts/keyless-zkir-bundle.mjs create \
  /absolute/full/managed/trust-registry \
  /absolute/new/keyless-managed \
  <signed-source-sha> \
  /absolute/pinned/compact-0.31.1/zkir
```

Record the returned `manifestSha256` in an authenticated release channel. The
manifest inside the directory is not a self-authenticating signature. A consumer
must supply that trusted digest when verifying or materializing:

```sh
node scripts/keyless-zkir-bundle.mjs verify \
  /absolute/keyless-managed <trusted-manifest-sha256>
node scripts/keyless-zkir-bundle.mjs materialize \
  /absolute/keyless-managed /absolute/new/full-managed \
  /absolute/pinned/compact-0.31.1/zkir <trusted-manifest-sha256> [jobs]
```

Materialization checks the binary digest and platform, verifies every input,
generates keys in a private temporary directory, checks every output hash,
and only then renames it into place. A failure leaves no accepted destination.
`jobs` defaults to one and is capped at four; large circuits can require several
GiB of RAM per worker, so choose concurrency for the operator host.
The output is a local full managed directory. A separate local packer can make
and verify a keyless contract tarball from the full contract package. It reads
the package's `pnpm pack --dry-run` file catalog without running lifecycle
scripts, requires exactly the manifest's key catalog in the source package,
removes those keys, and embeds the trusted regeneration manifest:

```sh
node scripts/pack-keyless-contract.mjs pack \
  /absolute/full/contracts/trust-registry \
  /absolute/keyless-managed <trusted-manifest-sha256> \
  /absolute/new/trust-registry-contract-keyless.tgz
node scripts/pack-keyless-contract.mjs verify \
  /absolute/trust-registry-contract-keyless.tgz \
  <trusted-tarball-sha256> <trusted-manifest-sha256>
node scripts/pack-keyless-contract.mjs materialize \
  /absolute/trust-registry-contract-keyless.tgz \
  /absolute/new/local-full-contract-package \
  /absolute/pinned/compact-0.31.1/zkir \
  <trusted-tarball-sha256> <trusted-manifest-sha256> [jobs]
```

The tarball digest must be authenticated out of band. The materialized package
is local and has the full keys only after their hashes match; it is not an npm
publication or a verified standalone installer. Both full and keyless packages
still need clean-consumer compatibility testing before publication.
`sourceRevision` is supplied by the caller; this utility does not independently
attest that the generated files came from that Git tree. The release builder
must bind the source and generated bytes under an approved signed commit.
Generation requires local CPU, memory, and roughly the original 6.7 GiB of
key storage. Keep the original full keys until all target-platform outputs have
been independently compared.

Before this can replace the standalone bundle, the release package builder,
manifest schema, installer, clean-consumer smoke, and deployment verifier must
accept a keyless transport followed by this fail-closed materialization. The
whole 66-circuit catalog must pass on the supported Linux target, including
failure/restart cases. A deployed verifier-key catalog must be checked against
the selected chain; predeployment uses regenerated verifier keys and the
approved manifest hashes. Do not infer deployed finality or actor E2E from a
key-generation match.

MIP-0020 proposes SDK-managed on-demand prover-key regeneration. It is not a
shipped dependency of this Ledger 8 local release; this experiment uses the
pinned `zkir` CLI and generates both key types before use.
